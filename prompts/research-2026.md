# Контекст задачи

Хакатон ЛЦТ 2026, кейс Департамента природопользования и охраны окружающей среды Москвы (ДПиООС): сервис автопроектирования озеленения улиц с учётом подземных коммуникаций. На вход DXF (геоподоснова, подземные сети, борта, здания, границы работ) и параметры участка, на выходе DXF с планом посадок деревьев, кустарников, газонов и типовых элементов скверов. Целевая аудитория: специалисты ДПиООС и подведомственных учреждений, проектировщики благоустройства, участники согласования.

Требования ТЗ, которые определяют оценку:
- главное это рабочий алгоритм или модель (правила, оптимизация, ML/ИИ или гибрид на выбор команды), результат корректный, воспроизводимый и объяснимый; UI вторичен, достаточно CLI;
- весь результат только на отдельных слоях, исходные слои, сущности, блоки и стили не изменяются; правки пользователя тоже только на слое результата;
- к каждой посадке и к каждому отказу объяснение со ссылкой на нормативный акт и конкретный пункт, таблицу или норму отступа; объяснения выгружаются в машиночитаемом файле (JSON, CSV, Markdown или PDF) и/или атрибутами на слое DXF; "чёрный ящик" без привязки к нормам не принимается;
- выходной DXF открывается в nanoCAD и других Linux-совместимых средствах, слой результата включается и выключается независимо;
- параметризация и повторный прогон (конфиг, аргументы CLI);
- обязателен Docker, Kubernetes по желанию, целевая ОС МосТех.ОС (x86-64 Linux, по среде близка к Ubuntu), Windows не целевая; HTTP API только с OpenAPI;
- профиль железа: от 8 логических ядер и 3 ГГц, 16 ГБ RAM (рекомендовано 32), GPU с 3D-ускорением от 4 ГБ VRAM (рекомендовано до 8), SSD;

- критерии жюри: идея и оригинальность подхода, прозрачность логики отступов и работы со слоями, качество интерпретируемости, обоснование выбора "алгоритм, ИИ или гибрид", воспроизводимость, устойчивость парсинга и записи DXF, скорость, трассировка "посадка -> норма -> пункт", корректность отступов, практическая применимость точек, полнота для передачи в CAD, путь внедрения в контур ДПиООС;
- бонус: фотореалистичные визуализации после финального DXF, согласованные с планом посадок.

# Целевая архитектура (гипотеза, подтверди или предложи лучше)

Python через uv, монорепо, конвейер из пакетов:
1. ingest: DWG -> DXF в контейнере (кандидаты ODA File Converter, запасной LibreDWG), регистронезависимый резолвер XREF, bind в один DXF с сохранением происхождения каждой сущности (ссылка вида <sha файла>:<хеш цепочки XREF>:<handle>).
2. semantics: классификация слоёв в классы объектов (сети по типам, борт, здание, граница работ, существующие деревья, покрытия) по имени слоя, суффиксу XREF, определению типа линии, подписям вдоль линий (диаметр), цвету, геометрии; редактируемый layer_map.yaml; LLM допускается только при генерации конфига и только офлайн.
3. rules: нормы как данные (acts.yaml, rules.yaml): стабильный rule_id отдельно от цитаты; у цитаты акт, редакция, пункт, дословный текст, URL, дата сверки, статус verified / unverified / not_found.
4. placement: буферы по правилам с учётом базы измерения (ось ствола, наружная стенка трубы, половина диаметра из подписи), зоны allowed / forbidden / needs_approval, существующие деревья из перечётной ведомости как препятствия; MVP жадная аллея вдоль борта, финал многокритериальная оптимизация (кандидат OR-Tools CP-SAT), контрфакты для отказов; компенсационная цель из перечётной ведомости как параметр.
5. explain: объяснения строго по шаблонам из трассы правил, без LLM в рантайме; независимый верификатор, что каждая ссылка резолвится в цитату.
6. dxf_out: ezdxf, слои GREEN_TREES, GREEN_SHRUBS, GREEN_HEDGES, GREEN_LAWN, GREEN_ZONES_*, GREEN_REJECT, GREEN_LABELS, GREEN_EDITS; блоки из условных знаков заказчика; видимые атрибуты (номер, вид, НПА) и XDATA; проверка неизменности исходных сущностей по отпечаткам.
7. eval: сравнение с эталонами проектировщиков, независимый чекер нарушений, нормоконтроль чужих проектов как второй сценарий для ДПиООС.
8. api и CLI: FastAPI с OpenAPI, CLI в том же образе, Docker на Ubuntu LTS.
9. бонус: инпейнтинг реальных фото "до" по маскам из проекции точек плана с измеренной согласованностью.

Принципы: fail-closed (нет данных о сетях или слой не распознан, значит не сажаем и пишем причину), детерминизм, офлайн-работа в закрытом контуре.

# Правила проверяемости

- Каждое утверждение о норме, версии, лицензии и возможности инструмента сопровождается ссылкой на первоисточник и датой обращения. Первоисточники по нормам: pravo.gov.ru, publication.pravo.gov.ru, mos.ru, docs.cntd.ru, base.garant.ru, consultant.ru, сайты Минстроя и ФАУ ФЦС для СП, Росстандарт для ГОСТ. По инструментам: сайт вендора, релиз-ноты, репозиторий, файл LICENSE, model card.
- Нормы и условия лицензий цитируй дословно, пересказ не принимается.
- Запрещено выдумывать номера пунктов, таблиц, значения, версии и цифры производительности. Нет подтверждения, пиши "не подтверждено"; нет источника, пиши "НЕ НАЙДЕНО" и где искал. Текст только из вторичного источника помечай "ВТОРИЧНЫЙ, требует проверки".
- Если в разных документах значения расходятся, не усредняй: дай обе строки и пометь "КОНФЛИКТ".
- Гипотезы о данных пилота (смысл суффиксов, система координат) без первоисточника остаются гипотезами.
- Форумы и обзоры только как подсказка, где искать первоисточник. Без маркетинга и воды.
- Критерий качества: эксперт берёт любую строку таблицы норм и за минуту находит цитату по ссылке. Лучше 40 подтверждённых строк, чем 120 непроверенных.
