# LCT_2026 — генеративное озеленение улиц (ЛЦТ 2026, кейс ДПиООС)

Кейс: по DXF участка (геоподоснова «Мосгеотреста» + сети) автоматически спроектировать посадки деревьев и кустарников с нормативными отступами, результат вернуть в DXF на отдельных слоях с объяснением каждой посадки по пунктам НПА. Пакет `green` в `src/` — рабочий вертикальный срез (Кирилл, 15.09.2026), см. `docs/architecture.md`.

## Стратегия: делаем максимум, цель — победа

Не «сдать минимум», а закрыть ТЗ целиком, включая желательное и бонус. MVP допустим только как **тонкий вертикальный срез той же архитектуры** (промежуточная сдача), который потом наращивается, а не переписывается. Правило проверки любого решения: «когда будем делать план-максимум, это придётся переделывать?» — если да, делаем сразу правильно.

Как это обеспечивается (целевая спека `docs/spec.md`, текущая архитектура — `docs/architecture.md`, оперативный план Кирилла — `docs/plan.md`):
- Гексагональное ядро `green.domain` + `green.application` без фреймворков (контракт import-linter); CLI, HTTP API и будущий веб — тонкие обёртки над одним кодом.
- Нормы как данные (`config/rules.yaml`, `config/acts.yaml`): `rule_id` стабилен, цитата и пункт меняются при смене редакции; объяснения строятся только из трассы правил, без LLM.
- Стратегии размещения за портом `PlacementStrategy`: жадная аллея вдоль борта сегодня, «заполнение газона» и CP-SAT завтра, тот же порт.
- Проверка целостности исходных сущностей и Docker на Linux — с первого дня.

Линт: `uv run ruff check src`, `uv run ruff format --check src`, `uv run ty check src`, `uv run lint-imports`.

## Конвенции

- Python 3.14, uv ≥0.12.15 (сборка через `uv_build`), ruff `select = ["ALL"]` с исключениями из `pyproject.toml`, тайпчекер ty, import-linter — всё должно быть зелёным перед коммитом.
- Ветки от `main`, conventional commits (у Кирилла: `feat(placement): …`, `docs: …`), squash в main. Ветка наших доков — `docs/dataset-research`.
- Датасет и ТЗ в git не кладём. Результаты прогонов — `runs/`, `out/` (игнорируются).
- Windows-грабли: `PYTHONIOENCODING=utf-8` для кириллицы в консоли; Git Bash переписывает аргументы с двоеточием (`origin/main:.gitignore`) — `MSYS_NO_PATHCONV=1`.

## Условия сдачи (из ТЗ ДПиООС, полный текст — `ТЗ/tz_dpioos_2026.txt`, локально)

Целевая среда проверки — НЕ машина разработчика:
- **ОС: МосТех.ОС** (Linux x86-64, по среде близка к Ubuntu). Windows не является целевой ОС. Разработка на Ubuntu-совместимом Linux допустима.
- **Железо стенда:** RAM от 16 ГБ (32 — для тяжёлых подоснов), CPU ≥3 ГГц и ≥8 логических ядер, GPU ≥4 ГБ VRAM под OpenGL (это для CAD-просмотра, не CUDA — на локальную LLM не рассчитывать), SSD 10–20 ГБ свободно, интернет «при необходимости».
- **Docker обязателен** (Dockerfile и/или docker-compose), поднимается по инструкции без привязки к машине разработчика. Kubernetes — по желанию. Если есть HTTP API — **обязателен OpenAPI/Swagger**.
- Результат проверяют в **nanoCAD или ином DXF-просмотрщике под Linux**, не в AutoCAD: исходные слои целы, слой результата читается.

Приоритеты жюри (в этом порядке):
1. Рабочий алгоритм/модель: DXF → обработка → DXF, результат **только на отдельных слоях** (у нас `GREEN_*`). Исходные слои не меняются и не перезаписываются.
2. **Интерпретируемость обязательна:** для каждой посадки и для каждого отказа у коммуникаций — объяснение со ссылкой на акт и пункт/таблицу (СП 42.13330 — с 12.07.2026 действует редакция 2026, 743-ПП, 623-ПП / МГСН 1.02-02). Выгрузка отдельным машиночитаемым файлом (JSON/CSV/MD/PDF) и/или атрибутами/подписями на слое результата. «Чёрный ящик» не принимается.
3. UI второстепенен: достаточно CLI / скрипта / минимальной формы. Правки — желательно, не блокирующе; минимум — перезапуск с другими параметрами.
4. Бонус: после финального DXF — реалистичные фото/AI-визуализации участка, согласованные с планом.

Сдача: промежуточная (DXF на вход → зоны/точки с базовыми отступами → план хотя бы для деревьев на отдельном слое → выходной DXF хотя бы упрощённый → черновик объяснений → описание логики → живой прогон на ноутбуке команды, CLI ок) и финальная (всё выше полностью + параметризация/повторный прогон + документация с BPMN-схемой или эквивалентом + Swagger при бэкенде + презентация 10–20 слайдов + демо 4–10 минут с проверкой DXF в CAD под Linux + файлы интерпретаций). Документация обязательна: назначение и границы, архитектура и схема развёртывания, описание алгоритма и механизма интерпретируемости, методы и библиотеки со ссылками, пошаговый запуск в Docker, ограничения и известные ошибки.

Критерии, за которые дают баллы: корректность отступов на тестовых DXF, устойчивость парсинга/записи DXF, время прогона участка, трассировка «посадка → норма → пункт», воспроизводимость, Docker (+K8s), Swagger.

## Терминология

«Эталон» / «эталонные решения» (слово из ТЗ) = планы проектировщиков из папок «Проектное решение». Это референс **формата и состава** выхода и тестовые данные, а не оптимум: план Берзарина содержит 306 нарушений отступов, перекладкой сетей это не объясняется. Цель генератора — расставить **лучше** измеримо: 0 нарушений при сопоставимом числе деревьев и площади крон, с объяснением по пунктам норм. У планов проектировщиков берём только паттерны (группы во дворах, изгороди вдоль проезжей части, ассортимент), не координаты.

## Открытые риски (15.09.2026)

- Нормы: 75 из 76 правил со сверенным основанием (не сверена охранная зона газопровода, она отключена в профилях), дословные цитаты СП 42.13330.2016 (п. 9.6, табл. 9.1), 743-ПП (табл. 3.6.1 с прим. 3, 3.6.2, п. 3.6.18), 623-ПП (п. 4.2.4, 4.2.8), ПП РФ N 160, 369-ПП (перечень и порядок по группам) (`docs/notes/07-norms.md`, `docs/notes/11-species-norms.md`). Нет текстов СП 42.13330.2026, ПП РФ N 878, правок 743-ПП 2026 года. Тип территории по 369-ПП и пол посадочного материала тополей в чертеже не определяются, это параметр профиля и допущение каталога. Берёза запрещена как массовый аллерген (п. 3.6.18), хотя проектировщик Берзарина её сажает. ТЗ называет редакцию СП 2016, действует 2026: если эксперты ждут пункты 2026, ссылки придётся переносить.
- Два приёма (аллея вдоль борта, сетка по газону), один вид на прогон, жадный отбор; CP-SAT, группы и подбор видов не сделаны. Эталон Олимпийской деревни: 59% деревьев проектировщика в 6 м от наших; Берзарина 301 против 318.
- Нормы строже практики: у Берзарина 41,8% деревьев проектировщика ближе 2 м к силовому кабелю. Нужен режим прикорневых барьеров (СП 42, табл. 9.1, прим. 5 и 7).
- Тесты: 215 (чтение блоков, аудит, ремонт строк, классификатор, целостность, сквозной прогон на синтетическом топоплане, подбор и квоты, видовые нормы, барьеры, комплект DXF, ведомость, единицы чертежа, HTTP API, откосы, неизменность исходного документа, нормоконтроль, цитаты актов при заданном `GREEN_LAWS_DIR`), `uv run pytest`. Нет тестов на реальных чертежах пилота. Нормоконтроль эталонов - команда `green audit` (`docs/notes/24-audit.md`): план проектировщика Берзарина 391 посадка с нарушениями из 554, наш план 0.
- ezdxf на генплане 309 тыс. сущностей: чтение+запись больше двух минут; на Берзарина 149 с (18.09.2026, `docs/notes/23-load-time.md`), из них чтение с ремонтом 55 с, сверка целостности 35 с. C-расширения ezdxf под Python 3.14 не собраны, математика идёт на чистом Python.
- LibreDWG 0.14 (и Windows, и Linux-сборка в образе) режет длинные строки посреди `\U+XXXX` и оставляет сырые переводы строк: загрузчик чинит это на запасном пути и нормализует документ через запись ezdxf, пустые `REGION` без ACIS при этом отбрасываются и перечисляются в предупреждениях. Блоки `msdElementType*` разбираются на геометрию, из `DIMTXT` берётся только текст (`docs/notes/04-issues-and-fixes.md`). Результат ни разу не открывали в nanoCAD/QCAD под Linux — сам прогон в контейнере проверен (16.09.2026, `docs/notes/10-assortment-runs.md`: Берзарина в образе даёт тот же план, что на Windows, целостность цела), а просмотр DXF глазами в Linux-просмотрщике остаётся невыполненным.
