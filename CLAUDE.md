# LCT_2026 — генеративное озеленение улиц (ЛЦТ 2026)

Кейс: по DXF участка (геоподоснова «Мосгеотреста» + сети) автоматически спроектировать посадки деревьев, кустарников и газонов с нормативными отступами от сетей и инфраструктуры и выгрузить результат обратно в DXF. Нужны правки текстом и графикой, веб-визуализация.

## Стратегия: делаем максимум, цель — победа

Не «сдать минимум», а закрыть ТЗ целиком, включая желательное и бонус. MVP допустим только как **тонкий вертикальный срез той же архитектуры** (промежуточная сдача), который потом наращивается, а не переписывается. Правило проверки любого решения: «когда будем делать план-максимум, это придётся переделывать?» — если да, делаем сразу правильно.

Как это обеспечивается (см. `docs/plans/2026-09-15-design.md`):
- Ядро — библиотека `greenplan` с чистыми функциями и pydantic-моделями; CLI, HTTP API и веб — тонкие обёртки над одним и тем же кодом.
- Единая внутренняя модель данных (Site / Rule / Solution / Explanation / Config) с первого дня; DXF только на входе и выходе.
- База норм с id пунктов и объяснения — с первого коммита, а не «захардкодим 2 м, потом переделаем».
- Планировщик за интерфейсом `Planner.plan(site, config, locked) -> Solution`: жадный линейный сегодня, CP-SAT завтра, та же сигнатура.
- Решение с самого начала хранит locked/edited элементы и параметры — редактор и текстовый агент потом меняют только config и locks.
- Docker, тесты на эталонах и проверка целостности DXF — с первого дня.

Стартовая точка любой сессии:
- `docs/DATA.md` — что где лежит, как достать улицу из 11-гигабайтного zip, как конвертировать DWG.
- `docs/RESEARCH.md` — устройство слоёв и блоков, эмпирика отступов в эталоне, предложенный пайплайн ядра, открытые вопросы.

## Условия сдачи (из ТЗ ДПиООС, полный текст — `docs/case/tz_dpioos_2026.txt`, PDF рядом)

Целевая среда проверки — НЕ машина разработчика:
- **ОС: МосТех.ОС** (Linux x86-64, по среде близка к Ubuntu). Windows не является целевой ОС. Разработка на Ubuntu-совместимом Linux допустима.
- **Железо стенда:** RAM от 16 ГБ (32 — для тяжёлых подоснов), CPU ≥3 ГГц и ≥8 логических ядер, GPU ≥4 ГБ VRAM под OpenGL (это для CAD-просмотра, не CUDA — на локальную LLM не рассчитывать), SSD 10–20 ГБ свободно, интернет «при необходимости».
- **Docker обязателен** (Dockerfile и/или docker-compose), поднимается по инструкции без привязки к машине разработчика. Kubernetes — по желанию. Если есть HTTP API — **обязателен OpenAPI/Swagger**.
- Результат проверяют в **nanoCAD или ином DXF-просмотрщике под Linux**, не в AutoCAD: исходные слои целы, слой результата читается.

Приоритеты жюри (в этом порядке):
1. Рабочий алгоритм/модель: DXF → обработка → DXF, результат **только на отдельных слоях** (например `PLANTING_PROPOSED`, `GREEN_AI_*`; допускается несколько: деревья/кустарники/покрытия). Исходные слои не меняются и не перезаписываются.
2. **Интерпретируемость обязательна:** для каждой посадки и для каждого отказа у коммуникаций — объяснение со ссылкой на акт и пункт/таблицу (СП 42.13330.2016, 743-ПП, 623-ПП / МГСН). Выгрузка отдельным машиночитаемым файлом (JSON/CSV/MD/PDF) и/или атрибутами/подписями на слое результата. «Чёрный ящик» не принимается.
3. UI второстепенен: достаточно CLI / скрипта / минимальной формы. Правки — желательно, не блокирующе; минимум — перезапуск с другими параметрами.
4. Бонус: после финального DXF — реалистичные фото/AI-визуализации участка, согласованные с планом.

Сдача: промежуточная (DXF на вход → зоны/точки с базовыми отступами → план хотя бы для деревьев на отдельном слое → выходной DXF хотя бы упрощённый → черновик объяснений → описание логики → живой прогон на ноутбуке команды, CLI ок) и финальная (всё выше полностью + параметризация/повторный прогон + документация с BPMN-схемой или эквивалентом + Swagger при бэкенде + презентация 10–20 слайдов + демо 4–10 минут с проверкой DXF в CAD под Linux + файлы интерпретаций). Документация обязательна: назначение и границы, архитектура и схема развёртывания, описание алгоритма и механизма интерпретируемости, методы и библиотеки со ссылками, пошаговый запуск в Docker, ограничения и известные ошибки.

Критерии, за которые дают баллы: корректность отступов на тестовых DXF, устойчивость парсинга/записи DXF, время прогона участка, трассировка «посадка → норма → пункт», воспроизводимость, Docker (+K8s), Swagger.

Коротко о грабле:
- В датасете только DWG. Конвертация: `tools/libredwg/dwg2dxf.exe` (нужен pre-release ≥0.14.8597, стабильная 0.14 пишет битый DXF).
- Читать DXF только через `ezdxf.recover.readfile`, загрузка 100–200 МБ занимает ~1 мин, поэтому парсим один раз и кэшируем.
- Геометрия подосновы лежит внутри блоков xref, блоки `DIMTXT` — это подписи со стрелками, а не сети.
- В git не идут `data/` и `tools/`.

Код пока только разведочный: `scripts/extract_street.py`, `scripts/research/*.py` (черновики). `uv`-проект ещё не инициализирован.
