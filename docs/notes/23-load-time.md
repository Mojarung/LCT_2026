# Время чтения большого чертежа: порядок загрузки (18.09.2026)

Время прогона участка входит в критерии жюри. На генплане Берзарина (99 МБ, 206 860 сущностей) прогон занимал 183 с, из них чтение 85 с.

## Шаг 1. Профиль

Скрипт `read_profile.py` (загрузка, аудит, единицы, обход под cProfile, отпечатки) на `gp.dxf`:

| Этап | Время |
|---|---|
| строгий загрузчик `ezdxf.readfile` | падает через 6,9 с: `Invalid group code` на строке 11 402 325 |
| режим восстановления `recover.readfile` на исходном файле | падает через 16,9 с: `ValueError: invalid literal for int() with base 16` |
| ремонт строк и `recover.read` на отремонтированных байтах | 37,1 с |
| итого загрузка | 60,9 с |
| аудит | 3,6 с |
| определение единиц | 1,4 с |
| обход блоков под профилировщиком | 55,3 с, без него около 27 с |
| отпечатки сущностей | 10,1 с |

Ещё два факта из профиля:

- `ezdxf.options.use_c_ext` равно `False`. У ezdxf 1.4.4 нет готовых колёс под Python 3.14, в `ezdxf/acc/` лежат только исходники `.pyx`. Вся векторная математика идёт на чистом Python: 9,8 млн конструкторов `Vec3` за обход.
- В обходе 32 с из 55 (под профилировщиком) занимает `Insert.virtual_entities()`: 218 780 вставок, каждая копирует и трансформирует сущности блока. Ещё 14,8 с - расчёт размера блока для признака «условный знак».

## Шаг 2. Что исправлено

24 с уходили на две попытки, которые на файлах от LibreDWG обречены. Новый порядок в `cad/documents.py`, функция `load_document`:

1. Строгий загрузчик.
2. При неудаче ремонт строк: склейка разорванных значений, замена оборванных `\U+`, удаление одиночных CR. Затем снова строгий загрузчик, на отремонтированных байтах (через временный файл: кодировку ezdxf определяет по заголовку сам).
3. Если и он не справился, режим восстановления на тех же байтах.

Почему понадобилось удаление одиночных CR. После ремонта строк строгий загрузчик всё равно падал: `Invalid group code "\n"` на строке 11 481 787. В файле один одиночный возврат каретки внутри значения. Текстовый режим Python считает его переводом строки, пары «код - значение» съезжают. Режим восстановления делит файл только по LF и этого не замечает. Проверка: `lone CR: 1, CRLF: 11 615 551`; после удаления строгий загрузчик читает файл за 17,4 с.

## Шаг 3. Проверка

Тесты `tests/test_documents_loader.py` (4): отремонтированный файл читается без режима восстановления, одиночный CR убирается и попадает в заметку, чистый файл заметок не получает, мусор вместо DXF даёт `InputError` с именем файла. Прежние тесты ремонта (`tests/test_documents_repair.py`) проходят без правок.

Берзарина, та же команда, что в `notes/18`, прогоны `out/check/berzarina_slopes` (до) и `out/check/berzarina_load` (после):

| Показатель | До | После |
|---|---|---|
| Чтение | 85,1 с | 55,2 с |
| Весь прогон | 183 с | 149 с |
| Посадок | 860 | 860, совпали все по координатам и видам |
| Отказов записано | 1 735 | 1 735, совпали все |
| Исходных сущностей без изменений | 206 860 | 206 860 |

Документ, загруженный строгим загрузчиком, держит в базе больше записей (384 338 против 379 460 у режима восстановления), но сцена, план и отпечатки исходника получаются теми же.

## Что осталось

| Что | Оценка выигрыша | Почему не сделано сейчас |
|---|---|---|
| Собрать C-расширения ezdxf в Docker-образе (`uv pip install --no-binary ezdxf`, нужны Cython и gcc в сборочном слое) | кратно на векторной математике: обход, запись, отпечатки | Docker на машине разработки не запущен, проверить сборку под Python 3.14 нечем. Вслепую Dockerfile не правим |
