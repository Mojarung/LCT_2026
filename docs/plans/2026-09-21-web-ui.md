# Веб-интерфейс: план реализации

> **Исполнителю:** шаги помечены чекбоксами. План писался под исполнение в той же сессии,
> поэтому в нём зафиксированы контракты, решения и критерии приёмки, а не вторая копия кода
> (наблюдение 0071). Там, где значение нельзя знать заранее — размер артефакта, время прогона, —
> стоит «измерить и записать», а не выдуманное число: подставленное наугад ожидание в плане
> удовлетворяется правкой реализации и перестаёт быть проверкой (наблюдения 0010, 0013).

**Цель:** веб-интерфейс к существующему ядру: загрузить чертёж, получить план, увидеть его на
карте с объяснением каждой посадки по пунктам НПА и поправить посадки руками с пересчётом норм.

**Архитектура:** FastAPI отдаёт HTML (Jinja2), навигация и опрос статуса на HTMX, карта плана —
отдельный vanilla-модуль на `<canvas>`, говорящий с `/api/v1`. Ноль node в образе, ноль запросов
в интернет в рантайме. Ядро (`green.domain`, `green.application`) не трогаем: веб — ещё одна
тонкая обёртка в `green.interfaces`, наравне с CLI и API.

**Стек:** FastAPI, Jinja2, HTMX (вендорим один файл в `static/`), vanilla JS + Canvas 2D, shapely
(уже в зависимостях) для упрощения геометрии подосновы.

**Спека:** `docs/spec.md`, условия сдачи в `CLAUDE.md` («Условия сдачи»), решения — раздел
«Решения» ниже.

## Глобальные ограничения

- Целевая среда — **МосТех.ОС (Linux x86-64) в Docker, интернет «при необходимости»**. Ни одного
  обращения в CDN из браузера: HTMX, шрифты, иконки — только локальные файлы. Проверяется
  вкладкой Network: внешних запросов ноль.
- **Ноль node в образе.** Если решение требует сборки фронта — решение неверное.
- Python 3.14, `ruff select = ["ALL"]`, тайпчекер `ty`, `lint-imports` — всё зелёное перед
  коммитом: `uv run ruff check src`, `uv run ruff format --check src`, `uv run ty check src`,
  `uv run lint-imports`, `uv run pytest`.
- **Контракт `/api/v1` не ломаем.** Новые эндпоинты добавляются, существующие схемы не меняются;
  `docs/openapi.json` перевыгружается (`uv run green openapi --out docs/openapi.json`).
- Слои результата остаются `GREEN_*`, исходные сущности не меняются — правка посадок в вебе
  обязана проходить через тот же `PlanWriter`, а не писать в DXF напрямую.
- Кириллица в шаблонах и в ответах: `PYTHONIOENCODING=utf-8` в окружении CLI, `charset=utf-8`
  в HTML.
- Ветка `feat/web-ui`, conventional commits, коммит в конце каждой задачи.

## Решения (приняты до плана, менять только с обоснованием)

1. **Подоснову на канву отдаёт новый артефакт `basemap.geojson`**, а не чтение DXF по запросу:
   чтение Берзарина занимает 55 с, для интерактива это неприемлемо. Артефакт пишется один раз
   во время прогона.
2. **Подоснова фильтруется и упрощается.** На генплане 309 тыс. сущностей — столько в браузер
   не отдать. Берём только классы, которые видно на карте (сети, борта, кромки покрытий, здания,
   газоны, дороги, тротуары, опоры, существующие деревья, граница работ), режем по границе работ
   и упрощаем с допуском. Числа «до» и «сколько осталось» **обязаны стоять рядом** в свойствах
   артефакта: отчёт, показывающий только выход, не отличает успешную обработку от молчаливой
   потери (наблюдение 0024).
3. **Проверка точки при перетаскивании — `ConstraintIndex`, живущий в памяти процесса**, ключ
   `run_id`, LRU на 2 прогона. Если индекса нет (сервис перезапустили) — `409` с внятным текстом
   «прогон нужно повторить». Персистентность сцены не делаем: для сценария «прогнал → правлю»
   она не нужна, а сериализация shapely на 300 тыс. объектов — отдельная задача с собственными
   граблями. Порт спроектирован так, чтобы персистентность подключалась позже без правки
   вызывающего кода.
4. **Правка двухступенчатая.** Перетаскивание даёт мгновенный вердикт (`POST …/check`, единицы
   миллисекунд). Перезапись DXF и артефактов — отдельная фоновая операция по кнопке
   («Пересобрать DXF»), потому что запись Берзарина занимает десятки секунд.
5. **Веб-страницы живут на `/`, данные — на `/api/v1`.** HTML-роутер не дублирует бизнес-логику:
   он берёт тот же `Container`.

**Места подключения, которые легко забыть** (наблюдение 0053): `create_app` монтирует статику и
веб-роутер; `.importlinter` получает новый модуль в контракте слоёв, иначе `lint-imports` упадёт
или, хуже, пропустит нарушение; `docker/Dockerfile` обязан копировать `templates/` и `static/`
в образ — иначе локально всё работает, а в контейнере пустая страница; `pyproject.toml` должен
включить эти каталоги в пакет (`uv_build` по умолчанию тянет только `.py`).

### Задача 1: Подоснова для карты — артефакт `basemap.geojson`

**Файлы:**
- Создать: `src/green/application/basemap.py`
- Изменить: `src/green/infrastructure/reports/artifacts.py` (добавить артефакт в `save`)
- Тест: `tests/test_basemap.py`

**Интерфейсы:**
- Потребляет: `Scene`, `Feature`, `ObjectClass` из `green.domain.objects`; `Plan` для границ.
- Производит:
  ```python
  @dataclass(frozen=True, slots=True)
  class Basemap:
      features: tuple[BasemapFeature, ...]   # geometry: BaseGeometry, object_class: ObjectClass
      features_in: int                       # сколько было на входе
      features_out: int                      # сколько попало в карту
      dropped_by_class: Mapping[str, int]    # класс -> сколько отброшено
      bbox: tuple[float, float, float, float]

  def build_basemap(scene: Scene, *, tolerance_m: float = 0.15) -> Basemap: ...
  ```
  GeoJSON пишет `artifacts.py`: `FeatureCollection`, `properties = {"class": <ObjectClass>}`,
  в `FeatureCollection` — поле `counts` с тремя числами выше и `crs_note` как у `zones.geojson`
  («координаты чертежа в метрах, не WGS84»).

- [ ] **Шаг 1.** Написать тест на синтетической сцене (взять фикстуру, которой уже пользуется
      сквозной тест прогона): отбираются только отображаемые классы, `IGNORE` и `UNKNOWN` не
      попадают, `features_in` равен числу объектов сцены, `features_out + сумма dropped_by_class`
      равняется `features_in`. Последнее — главный инвариант: он и ловит молчаливую потерю.
- [ ] **Шаг 2.** Прогнать, убедиться, что падает на отсутствующем модуле.
- [ ] **Шаг 3.** Реализовать `build_basemap`: фильтр по классам, `shapely.simplify` с допуском,
      отбрасывание пустых геометрий после упрощения (они тоже идут в `dropped_by_class`).
- [ ] **Шаг 4.** Прогнать тест — зелёный.
- [ ] **Шаг 5.** Подключить артефакт в `ArtifactSink.save`, дописать имя в докстринг модуля
      и в описание `GET /runs/{id}/artifacts/{name}`.
- [ ] **Шаг 6.** **Измерение на настоящем чертеже** (наблюдение 0021: проверка на реальных
      данных приходит извне текста и ловит то, чего не видно в плане). Прогнать Берзарина,
      записать в `docs/notes/25-web-ui.md`: размер `basemap.geojson` в МБ, `features_in`,
      `features_out`, время построения. **Критерий приёмки: файл ≤ 8 МБ.** Больше — поднять
      допуск упрощения и/или резать по границе работ, измерить заново и записать оба замера.
- [ ] **Шаг 7.** Коммит: `feat(web): basemap.geojson artifact for the plan viewer`.

- Производит:
  ```python
  @dataclass(frozen=True, slots=True)

      y: float | None
  ```

  ```
  POST /api/v1/runs/{run_id}/edits   {"edits": [...]} -> 200 сводка нового плана
  ```

  `openapi.json`. Бонус-визуализации и презентация этим планом не покрыты — это отдельные работы.
- **Заглушки.** Значения, которые нельзя знать до запуска (размер `basemap.geojson`, время
  отрисовки), помечены как измеряемые с записью в заметку; порог приёмки 8 МБ задан явно.
- **Согласованность типов.** `Basemap`/`build_basemap` (задача 1) потребляются только артефактами;
  `Edit`/`apply_edits` (задача 5) используют `ConstraintIndex` из задачи 4 — имя и сигнатура
  `evaluate(points) -> EvaluationBatch` взяты из существующего кода, не выдуманы.

## Что изменилось при исполнении (21.09.2026)

План писался до замеров, поэтому три решения пришлось поменять, и это важнее самих правок:

1. **HTMX не взяли.** Динамики оказалось ровно на две вещи - опрос статуса и канва, это десять
   строк ванили. Вендоренная зависимость ради двух подмен фрагмента не окупалась, а без неё
   требование «ноль внешних запросов» выполняется по построению.
2. **Порог приёмки был сформулирован неверно.** «`basemap.geojson` ≤ 8 МБ» - про файл на
   диске, а значение имеет то, что уходит в браузер. Замеры: 33,56 МБ при полной точности
   координат, 12,89 МБ на сантиметровой сетке, **1,3 МБ по проводу** после gzip. Отсечка по
   границе работ оказалась бесполезной для размера (лишних объектов 2 тысячи из 92), но
   необходимой для вида - карта подгоняется под план, а не под подоснову.
3. **Понадобился новый артефакт `rules.json`.** `plan.json` несёт только `rule_id`, а
   `interpretations.json` на Берзарина весит 51,8 МБ. Без маленького свода норм карта не
   смогла бы показать пункт акта, то есть задача 3 шаг 3 была нереализуема как написана.

Опасение про Dockerfile не подтвердилось: `uv_build` кладёт `templates/` и `static/` в колесо
сам, проверено сборкой колеса и установкой в чистое окружение. Контракт `.importlinter` тоже
править не пришлось - `green.interfaces.web` уже покрыт слоем `green.interfaces`.

Найденный и исправленный дефект: правка могла выдать посадку с вердиктом «запрещено», а
писатель такую посадку клал на слой `GREEN_TREES_APPROVAL`. Генератор подобного не производит,
поэтому раскладка по слоям этого случая не знала. Теперь нарушающая посадка становится
отказом и уходит на `GREEN_REJECT` (`docs/notes/25-web-ui.md`).
