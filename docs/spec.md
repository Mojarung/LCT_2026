# GreenPlan — спецификация решения кейса ДПиООС (ЛЦТ 2026)

Версия 0.1, 2026-09-15. Статус: черновик на ревью команды.
Основания: ТЗ — `ТЗ/tz_dpioos_2026.txt`; данные — `docs/notes/07-dataset-map.md`; разведка форматов и эмпирика отступов — `docs/notes/08-berzarina-layers-and-offsets.md`.
Рабочее имя пакета — `greenplan` (переименовать можно в любой момент, это одна строка в `pyproject.toml`).

## 1. Цель и стратегия

Цель — победа: закрыть ТЗ целиком (обязательное, желательное, бонус) и добавить то, что жюри не просило, но оценит: валидатор, который находит нарушения в эталонных проектах, батч по всем 20 улицам, калибровку ассортимента и шагов на реальных проектах, веб-редактор и текстовые правки.

Промежуточная сдача — не «отдельный MVP», а тонкий вертикальный срез той же архитектуры. Правило для любого решения: «при плане-максимум это придётся переделать?» — если да, делаем сразу правильно.

Принципы, которые обеспечивают рост без переписывания:

1. Ядро — библиотека `greenplan` с чистыми функциями и pydantic-моделями. CLI, HTTP API и веб — тонкие обёртки над одним кодом.
2. Единая внутренняя модель данных (§4) с первого дня. DXF только на входе и на выходе, внутри — shapely-геометрия и модели.
3. База норм с id пунктов и объяснения — с первого коммита: интерпретируемость по ТЗ обязательна, дописать её потом поверх «захардкоженных 2 м» нельзя.
4. Планировщик — за интерфейсом `Planner.plan(site, feasibility, config, locked) -> Solution`. Первая реализация жадная линейная, следующая — CP-SAT, сигнатура одна.
5. `Solution` с самого начала хранит закреплённые и пользовательские элементы и полный `Config`; редактор и текстовый агент потом меняют только config и locks и вызывают тот же планировщик.
6. Валидатор независим от генератора и работает на любом плане: нашем, отредактированном, эталонном.
7. Docker, CI на Linux, тесты на эталонах и проверка целостности DXF — с первого дня, потому что целевая среда — не машина разработчика.

## 4. Модель данных (pydantic v2, геометрия shapely, сериализация в WKB/GeoJSON)

- `Feature(id, geom, layer, block, source_xref, cls: str | None, attrs: dict, hidden: bool)` — любой объект входа с происхождением.
- `Site(id, source_path, bbox, features, boundary: Polygon | None, plantable: MultiPolygon | None, unclassified_layers: list[str], meta)`.
- `Rule(id, act, clause, table, row, quote, url, applies_to: list[str], offsets: dict[PlantingType, float | None], hardness: hard | soft | recommendation, modifiers: list[Modifier])`; `Modifier(condition, delta | factor, quote)` — например «кабель в футляре», «крона > 5 м».
- `PlantingType`: `tree_large`, `tree_medium`, `tree_small`, `shrub`, `hedge`, `lawn`, `flowerbed`.
- `Species(id, name_ru, name_lat, ptype, crown_r, height, spacing_min, tolerances{salt, shade, compaction, drought}, restrictions{invasive_369, near_playground, under_lep}, decorative: list[str], sources: list[str])`.
- `Module(id, name, pattern: row | group | hedge | solitaire | flowerbed | square, params, sources)`.
- `Config(scenario, territory_type, ptypes_enabled, species_whitelist, species_blacklist, spacing_overrides, weights{coverage, diversity, rhythm, margin, cost}, relaxations: list[Relaxation], layer_overrides, export_profile, seed)`.
- `Zone(id, ptype, kind: allowed | forbidden | potential, polygon, reasons: list[RuleRef], context)`.
- `Candidate(id, xy, ptype, zone_id, context)`.
- `Planting(id, ptype, species_id, xy, crown_r, module_id, locked: bool, origin: generated | user, checks: list[Check])`.
- `Check(rule_id, feature_id, distance, required, status: ok | violation | relaxed, relaxation_id)`.
- `Explanation(planting_id, summary_ru, why_here: list[str], checks, citations: list[Citation])`; `Citation(act, clause, table, row, quote, url)`.
- `Solution(id, site_id, config, plantings, zones, areas: list[Area], stats, version, parent_id, created_at)`.
- `IntegrityReport(unchanged: bool, input_layers: dict[str, LayerDigest], output_layers, added_layers, diff)`.

## 5. Пайплайн

**Стадия 1. Импорт.** `ezdxf.recover` → обход INSERT с трансформациями → `Feature` с происхождением. Служебные блоки подписей (`DIMTXT`, `msdElementTypeTextNode`) не геометрия, а источник атрибутов. Две версии подосновы дедуплицируются. Кэш GeoParquet: первый разбор минута, дальше секунды. Вход DWG для наших данных — через конвертер (ODA File Converter предпочтительнее LibreDWG, он ближе к тому, что выдаст жюри). Выход: `Site`.

**Стадия 2. Семантика.** YAML-правила для стандартных слоёв Мосгеотреста (пишутся один раз) → классы. Незнакомые слои → отчёт `unclassified_layers` + подсказки (LLM опционально) → пользователь подтверждает через `Config.layer_overrides` (CLI) или мастер слоёв (веб). Атрибуты сетей из подписей. Существующие деревья получают заключение из перечётной ведомости, если она подана («Сохранить» — препятствие с кроной, «Удалить» — нет).

**Стадия 3. Нормы.** `kb.yaml`: каждое правило с актом, пунктом, таблицей, строкой, цитатой и ссылкой. Ориентир — СП 42.13330.2016 табл. 9.1 (здание 5/1.5; край тротуара 0.7/0.5; проезжая часть 2/1; опора освещения 4/—; газопровод и канализация 1.5/—; теплосеть 2/1; водопровод и дренаж 2/—; силовые кабели и кабели связи 2/0.7 для дерева/кустарника; кроны более 5 м — отступ увеличивается), 743-ПП (те же отступы плюс московские требования), 623-ПП / МГСН, ПУЭ и ПП РФ №160 для охранных зон ЛЭП по напряжению, СП 42 треугольники видимости на перекрёстках, СП 59 минимальная ширина прохода при посадке в решётки, 369-ПП запрет инвазивных видов, 515-ПП рекомендуемый ассортимент, ТСН 30-307 плотность посадок. Все цифры и номера пунктов выписываются из первоисточников с цитатами до фазы 2 (`docs/RULES.md`), в фазе 1 — минимальный набор из табл. 9.1 с пометкой «проверить».

**Стадия 4. Пригодность.** Для каждого типа посадки: `F = озеленяемое ∩ граница − ⋃ buffer(объект, отступ)`. Векторно на shapely/GEOS с STRtree; растр 0.5 м только для тепловой карты. Озеленяемое = газоны подосновы и проекта; при отсутствии — всё внутри границы кроме проезжей части, тротуаров и зданий (переключатель в конфиге). Выход: зоны allowed/forbidden с причинами, статистика площадей, потенциал (асфальт и парковки без ограничений, которые можно превратить в газон — практика проектировщиков из эталонов).

**Стадия 5. Генерация.** Библиотека типовых модулей: рядовая посадка с шагом по породе, группа «дерево + 5–7 кустов», живая изгородь вдоль проезжей части, солитер, цветник у входов и остановок, сквер «аллея + группы». Полосы — `planner.linear`: осевая линия зоны, кандидаты 0.5 м, 1D-динамика по шагу. Площади — `planner.area`: гекс-сетка, CP-SAT MWIS (конфликт = кроны пересекаются). Породы после позиций: фильтр по контексту (ширина, соль у дороги, тень, площадка, ЛЭП, инвазивность) + разнообразие 10-20-30. Кустарники и изгороди в остатке для кустарников, газон и цветники — в остатке для покрытий. Целевая функция взвешенная, веса в конфиге, seed фиксирован — прогон воспроизводим.

**Стадия 6. Валидация.** `rules.validator` на любом `Solution`: для каждой посадки — проверка по всем классам препятствий в радиусе поиска, не только ближайшему. Результат — `Check` со статусами, из них строятся объяснения и отчёт конфликтов. На эталонах даёт слайд «в эталоне Берзарина 306 нарушений, у нас 0».

**Стадия 7. Правки.** Фаза 1: изменить конфиг и перезапустить (`greenplan run --set spacing.tree_large=7 --set species.blacklist=picea`), `greenplan diff a b`. Фаза 3: `edit.ops` (lock, move, delete, replace_species, add_zone forbid/require/lawn, set_param) → пересчёт с закреплёнными элементами; веб-редактор на карте; `edit.agent` — текст «убери хвойные у остановок, больше цветущих» → операции (rule-based парсер частых команд, LLM с JSON-схемой при наличии ключа). LLM никогда не ставит деревья и не считает отступы.

**Стадия 8. Экспорт.** DXF с результатом на слоях `GREEN_AI_*` (§7), объяснения (§6), отчёты: ведомость посадочного материала, паспорт объекта, ПЗ раздел «Озеленение» по структуре реальной ПЗ (существующее положение из перечётки, проектные решения, ассортимент, баланс территории — те же цифры, что в эталонной ПЗ: устраиваемый/восстанавливаемый/сохраняемый газон, деревья/кустарники, вырубка), отчёт конфликтов, GeoJSON.

**Стадия 9 (бонус). Визуализации.** После финального DXF: планшет-рендер (вид сверху с кронами, покрытиями, легендой) и AI-визуализации по «фото до» из датасета через img2img/inpainting с промптом из ассортимента решения. Считается на машине команды или через API, в целевую среду не входит.

## 6. Интерпретируемость

- Каждое правило в `kb.yaml` несёт акт, номер пункта, таблицу и строку, цитату текста и ссылку на источник. Объяснение никогда не ссылается на пункт, которого нет в базе.
- Для каждой посадки: `why_here` (зона и её контекст, модуль, причины выбора породы со ссылками на каталог и акты) + полный список `Check` по всем классам препятствий рядом: «кабель электрический — 2.7 м при норме 2.0 м, СП 42.13330.2016 табл. 9.1, строка “силовые кабели и кабели связи”».
- Для отказов: зоны `forbidden` с причинами и слой `GREEN_AI_ZONES_NO`; отклонённые кандидаты у коммуникаций — в JSON с правилом и расстоянием (требование 2.8 ТЗ).
- Форматы: `explanations.json` (машиночитаемый, по id посадки), `explanations.csv`, `report.md` и `report.pdf` (человекочитаемый, с цитатами пунктов), в DXF — слой `GREEN_AI_NOTES` с короткой подписью у каждой посадки и XDATA (appid `GREEN_AI`) с id и сводкой на самой сущности.
- Тексты объяснений шаблонные и детерминированные. LLM к ним не допускается, чтобы не выдумать пункт; допустима только переформулировка сводки, ссылки вставляются программно.

## 7. DXF: слои результата, совместимость, целостность

- Слои: `GREEN_AI_TREES`, `GREEN_AI_SHRUBS`, `GREEN_AI_HEDGES`, `GREEN_AI_COVER` (газон, цветники), `GREEN_AI_ZONES_OK`, `GREEN_AI_ZONES_NO`, `GREEN_AI_POTENTIAL`, `GREEN_AI_NOTES`, `GREEN_AI_LEGEND`. Второй профиль экспорта — «как у проектировщика» (`06_ДП_<Порода>_план`, выноски, разбивочные размеры на `GREEN_AI_DIMS`, ведомость таблицей) для передачи в реальное проектирование.
- Сущности простые: CIRCLE (крона), INSERT упрощённого блока-символа породы (линии и дуги, база — «Шаблоны значков.dwg»), LWPOLYLINE (группы, зоны), TEXT (не MTEXT и не MLEADER), HATCH только в профиле проектировщика. Версия файла R2010, кириллица через `\U+XXXX`. Проверка открытия в LibreCAD, QCAD и nanoCAD.
- Исходные слои не меняются: запись через ezdxf «загрузить → добавить → сохранить», затем `IntegrityReport` — по каждому исходному слою число сущностей, набор хендлов и хэш геометрии до и после; набор слоёв на выходе = входной + `GREEN_AI_*`. Если на файлах жюри пересохранение портит проприетарные объекты, включается режим splice: сущности и определения слоёв дописываются в текст исходного DXF без пересериализации остального.
- Дополнительно `result_only.dxf` — только слои результата, для наложения XREF.

## 8. Конфигурация и повторный прогон

YAML-сценарий = «набор параметров тестового участка» из ТЗ: тип территории, включённые типы посадок, ассортимент (белый/чёрный список), шаги, веса целевой функции, послабления (сеть в футляре, недействующая), переопределения слоёв, профиль экспорта, seed. CLI принимает `--config` и `--set key=value`; `greenplan diff` сравнивает два решения (число посадок, ассортимент, покрытие, конфликты). Это и есть требуемая ТЗ «демонстрация вариативности».

## 9. HTTP API и веб (фаза 3)

FastAPI с автогенерируемым OpenAPI (`/docs`): `POST /projects` (загрузка DXF, фоновый разбор), `GET/PUT /projects/{id}/layers` (маппинг слоёв), `POST /projects/{id}/analyze`, `POST /projects/{id}/solutions` (config → решение), `GET /solutions/{id}` (GeoJSON, статистика, объяснения), `POST /solutions/{id}/ops` (правки), `POST /solutions/{id}/chat` (текстовые правки), `GET /solutions/{id}/export/{dxf|report|xlsx|docx}`, `GET /jobs/{id}`. Веб: React + MapLibre в локальных координатах (система МГГТ закрытая, автоматической привязки к подложке нет; ручная привязка по двум точкам — опция для data.mos.ru), панели слоёв, правил, объяснений по клику, правки, версии, чат.

## 10. Тестирование и метрики

- Фикстуры: Берзарина (полный комплект) + Харьковская, Старый Гай, Наташинский, Харьковский проезд, Куликовская. Для тестов хранится усечённый DXF (фрагмент улицы), полные — в `dataset/`.
- Unit: движок норм (отступы по классу, типу, модификаторам), пригодность на синтетическом участке, планировщики на синтетике (нет пересечений крон, шаг соблюдён, закреплённые не двигаются), полнота объяснений (у каждой посадки есть проверка по каждому классу препятствий в радиусе), writer (целостность, набор слоёв, открытие ezdxf audit без ошибок).
- Golden-тесты: решение на фикстуре при фиксированном seed стабильно.
- Валидатор на эталонах: отчёт по всем улицам с эталоном.
- Метрики качества: 0 нарушений жёстких норм; доля пригодной площади, занятая посадками; индекс разнообразия; сравнение с эталоном по числу посадок и площади крон.
- Производительность: полный прогон улицы с кэшем < 60 с, первый разбор < 2 мин; замеры в отчёте прогона.
- CI: GitHub Actions на Ubuntu с первого коммита, ловит Windows-специфику путей и кодировок; сборка Docker-образа в CI.

## 11. Развёртывание и документация

- `docker/Dockerfile` на `python:3.12-slim` + `uv sync --frozen`; `docker-compose.yml` (api, web); `k8s/` манифесты как плюс. GPU не нужен. LLM подключается переменными `GREENPLAN_LLM_URL` / `GREENPLAN_LLM_KEY`, без них работает rule-based режим.
- Документация: `README.md` (запуск за 5 команд, пример прогона на улице из набора), `docs/ALGORITHM.md` (текст + BPMN-схема от входного DXF до выходного и бонуса; Mermaid для репозитория, экспорт PNG/PDF для сдачи), `docs/ARCHITECTURE.md` (компоненты, потоки, деплой), `docs/RULES.md` (таблица норм с цитатами и ссылками), `docs/LIMITATIONS.md`, `docs/DEMO.md` (сценарий 4–10 минут), Swagger.
- Презентация 10–20 слайдов по списку ТЗ: проблема, архитектура, алгоритм со схемой, слои DXF, пример объяснения, «до/после» на улицах пилота, источники и нормы, запуск, бонус, ограничения и масштабирование.

## 12. Фазы

Каждая фаза заканчивается работающим продуктом; следующая добавляет, а не переписывает.

**Фаза 1 — вертикальный срез (промежуточная сдача).** Каркас `uv`, модели, `io.dxf_reader` (bound xref + взорванные) с кэшем, `semantic.classify` по YAML для подосновы Мосгеотреста, `rules.kb` с правилами табл. 9.1 СП 42 и 743-ПП, `rules.engine`, `analysis.feasibility` для деревьев, `planner.linear`, `rules.validator`, `explain` в JSON + `GREEN_AI_NOTES`, `io.dxf_writer` с целостностью, CLI `run/analyze/validate`, Dockerfile, CI, README и краткий `ALGORITHM.md`. Проверка: Берзарина и ещё одна улица, DXF открыт в LibreCAD/QCAD.

**Фаза 2 — полный генератор.** Кустарники, изгороди, покрытия, модули, каталог пород (паспорта объектов + 515-ПП + 369-ПП), `planner.area` на CP-SAT, контекст (соль, тень, остановки, площадки), ЛЭП и треугольники видимости, потенциал (асфальт → газон), дедупликация версий подосновы, атрибуты из подписей, полный охват объяснений и отчёты (ведомость, паспорт, ПЗ, баланс, конфликты), профиль экспорта «как у проектировщика» с привязками, батч по 20 улицам, калибровка приоров на эталонах, `docs/RULES.md` с цитатами.

**Фаза 3 — API, веб, правки.** FastAPI + Swagger + фоновые задачи, React + MapLibre, мастер слоёв, редактор (lock/move/delete/зоны), версии решений, `edit.agent` (rule-based + LLM опционально), LLM-подсказки слоёв, docker-compose с веб.

**Фаза 4 — сдача.** Документация полностью (BPMN, деплой, ограничения), презентация, репетиция демо на Linux (VM/WSL2 с nanoCAD или QCAD), бонус-визуализации, k8s-манифесты, геопривязка и data.mos.ru при наличии времени, полировка.

## 13. Риски и меры

| Риск | Мера |
|---|---|
| DXF жюри отличается от наших (unbound xref, другие слои, взорванная геометрия) | три формы входа в reader, мастер слоёв, тесты на 6 улицах, конвертация фикстур ODA-конвертером |
| Пересохранение через ezdxf портит проприетарные объекты | `IntegrityReport` в каждом прогоне, режим splice |
| Linux-просмотрщики не рендерят сложные сущности | только простые сущности на слоях результата, проверка в LibreCAD/QCAD/nanoCAD |
| Цифры и пункты норм по памяти | выписать из первоисточников с цитатами до фазы 2, спросить экспертов кейса в чате |
| Время прогона | кэш, STRtree, упрощение геометрии, профилирование в CI |
| Перерасход объёма («максимум») | фазы с законченным продуктом на каждой; ядро вперёд, обёртки потом |
| Windows-специфика | CI и Docker на Linux с первого дня |
| LLM недоступна на демо | rule-based режим по умолчанию, LLM только как плагин |
