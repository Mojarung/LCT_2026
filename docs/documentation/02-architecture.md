## 2. Архитектура {#architecture}

### 2.1. Принципы

1. **Гексагональное ядро.** Алгоритм (`green.application`) и модель (`green.domain`) не
   зависят от фреймворков и форматов. Чтение и запись DXF, конвертеры, конфиги, HTTP и
   хранение подключаются адаптерами через порты. Контракт проверяет `import-linter`
   (`uv run lint-imports`). Первый контракт задаёт порядок слоёв: interfaces → bootstrap →
   infrastructure → application → domain. Второй запрещает ядру импортировать `ezdxf`,
   `fastapi`, `starlette`, `pydantic`, `granian`, `cyclopts`, `yaml`, `orjson`, `structlog`.
   CLI, HTTP API и веб-интерфейс - тонкие обёртки над одним сценарием `PlanSite`.
2. **Нормы - данные, а не код.** Расстояния, основания и видовые ограничения лежат в
   `config/rules.yaml`, акты - в `config/acts.yaml`. Смена редакции акта меняет пункт и цитату
   правила, а `rule_id` остаётся тем же, поэтому объяснения и интерпретации ссылаются на
   стабильный идентификатор.
3. **Генератор не проверяет сам себя.** План, собранный генератором, заново проверяет
   `validate_plan`. Он сам измеряет все расстояния для окончательных координат и видов и не
   доверяет сохранённым проверкам генератора; от генератора берёт только распознанные
   объекты и карту покрытий. Записанный DXF заново читается и сверяется с планом и
   исходником. Экспорт идёт только после обеих проверок (разд. 3.10, 3.12).
4. **Отказ вместо догадки.** Нечитаемая геометрия и неопознанный класс объекта
   останавливают расчёт. Без границы работ места не допускаются, без данных о сетях вердикт
   места - «нет данных»; оба случая названы в журнале прогона. Молчаливого допущения «здесь
   можно сажать» нет.
5. **Воспроизводимость.** Одинаковый вход, профиль и версия правил дают одинаковый план,
   пока не сработал ни один лимит времени: бюджет портфеля (900 с), таймаут MILP отбора
   (5 с) и подбора видов (60 с), бюджет сдвига посадок (30 с). На медленной машине лимит может
   сработать раньше, и набор посчитанных вариантов будет другим; это записано в
   `portfolio.json` и `selection.json`. Бюджеты портфеля, отбора и сдвига - параметры
   профиля (`portfolio_budget_s: 0` снимает бюджет портфеля), лимит подбора видов задан в
   коде. Отпечатки конфигов, версии пакетов и время этапов лежат в
   `run_manifest.json`. Кустанайская в Docker на Linux дала тот же план, что на Windows:
   861 посадка, 425 отказов.

### 2.3. Жизненный цикл прогона

1. `POST /api/v1/runs` (или форма, или улица из каталога) сохраняет вход в
   `runs/<id>/input/` и регистрирует прогон со статусом `queued`. Идентификатор - UUIDv7,
   поэтому порядок имён совпадает с порядком создания.
2. Фоновая задача выполняет `RunService.execute`. Одновременно считаются не больше
   `GREEN_MAX_PARALLEL_RUNS` прогонов (2). Статус `running` показывает этап, долю и оценку
   остатка времени (`application/progress.py`: веса этапов из замеров).
3. `PlanSite.execute` проходит конвейер из разд. 3 и возвращает отчёт прогона. Артефакты
   пишутся в `runs/<id>/output/`, статус становится `succeeded` или `failed` с причиной.
4. Контекст правки сохраняется в `runs/<id>/context.pickle`: прочитанный чертёж, план,
   отчёт, карта покрытий. Правка на карте поднимает его с диска и после перезапуска сервиса.
   Контекст, сохранённый другой версией кода, не поднимается (отпечаток исходников пакета).
5. Прогон, пока идёт, держит блокировку файла `runs/<id>/lease`. Если процесс умер, ОС
   снимает блокировку, и такой прогон при чтении помечается прерванным с причиной.
6. Перед новым прогоном самые старые законченные прогоны удаляются, пока каталог больше
   `GREEN_RUNS_MAX_GB` (8 ГБ в `compose.yaml`). Идущий прогон не удаляется никогда.

Образ собирается многостадийно (`docker/Dockerfile`):

1. бинарник uv 0.12.15;
2. LibreDWG 0.14 из исходников;
3. сборка веб-интерфейса в `node:24-slim`, Node в итоговом образе не остаётся;
4. окружение Python 3.14 через `uv sync --locked --no-dev` строго по `uv.lock`;
5. итоговый образ `ubuntu:26.04`: пользователь `green` (uid 10001, без прав root), проверка
   здоровья `GET /api/v1/health` каждые 30 с.

Во время работы сервис не обращается к сети и не использует внешних сервисов и баз
данных. Состояние - файлы в томе прогонов.

Требования к стенду: памяти - от 16 ГБ; пиковая память прогона самой тяжёлой улицы пилота -
{{peak_memory}} (замер в приложении B), поэтому два прогона тяжёлых улиц одновременно на
16 ГБ - предел. Процессор - 8 логических ядер; диск - образ 0,9 ГБ плюс том прогонов до
предела `GREEN_RUNS_MAX_GB`. Время прогонов по улицам - приложение B.

### 2.5. Производительность

- **Портфель вариантов** считается в пределах бюджета `portfolio_budget_s` (900 с).
  Варианты идут по ценности: исходный, совместный отбор, сетка по грунту, по борту, сдвиги
  сетки. Следующий вариант не начинается, если самый долгий из посчитанных не укладывается в
  остаток бюджета. Исходный вариант считается всегда. Пропуски записаны в `portfolio.json`.
- **Индекс чертежа** (объекты по классам, деревья поиска STRtree, твёрдые покрытия, граница
  работ) строится один раз на прогон и общий для всех вариантов. Проверки одной и той же
  пачки точек теми же правилами запоминаются. Предел памяти - 20 млн ячеек «правило ×
  точка».
- **Карта покрытий.** Кольцо грани проверяется по соседним кускам объединения линий
  материала, а спорные кольца - по объединению целиком. На Куликовской, самой тяжёлой по
  карте покрытий улице, этап занимает 25 с.

Замеры по улицам - приложение B.
